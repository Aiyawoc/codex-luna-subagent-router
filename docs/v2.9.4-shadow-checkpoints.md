# v2.9.4-rc.1 — Planner-integrated Decision Shadow

Date: 2026-11-02. Base: v2.9.3 / `3bd61e6e0ac693258efa03fbb109e3b4085cf4dc`.

## Why this change

A successful standalone Provider/Shadow probe proves connectivity, not routine use. Previous code exposed a manual `decision_shadow` command and Skill guidance but did not invoke it from the normal planner entrypoint. This candidate adds that missing connection without granting the decision model authority over execution.

## Implemented path

`route_advisor plan` → deterministic plan → shared plan_id + planning row → considered event → consent/evidence/checkpoint checks → atomic duplicate/rate-budget reservation → one provider dispatch → correlated decision result and terminal event.

Pure `plan_work()` and `recommend` remain network-free. The planner output includes only an observation status, IDs, reason and latency, **not provider answers**. Worker model/effort, execution shapes, permission limits and the nested RoutePlan are never rewritten by Shadow.

Every new planning observation has the same 32-hex plan_id as the returned plan. `origin=planner` answer rows carry this ID and the event checkpoint_id, plus a task hash and enum-only baseline axes. Manually invoked Shadow rows carry `origin=manual`; old rows remain source-unknown. No historical ledger is rewritten.

## Opt-in and bounded costs

Automatic calls require four explicit fields: `enabled=true`, `mode=shadow`, `setup_completed=true`, **`automatic_checkpoints=true`**. Existing enabled providers are not silently converted into automatic billable traffic. Q7 asks for the new choice without changing its existing provider; an explicit no is remembered.

After a controlled upgrade, the local Agent can enable the feature without reading or re-entering an existing Keychain credential:

```bash
bin/router configure_decision_engine --scope user --provider openai_decisions \
  --automatic-checkpoints on --json
```

The command preserves the same provider's credential source/scope and prior timeout. New OpenAI setups default to 5000ms, existing explicit settings are retained. Configure the effective project scope if a project routing.json overrides the user config.

Limits under `decision_engine.checkpoint_limits`:

| Setting | Default | Meaning |
| --- | ---: | --- |
| max_calls_per_24h | 20 | Rolling 24-hour automatic provider attempts across the same CODEX_HOME |
| min_interval_seconds | 30 | Minimum time between automatic attempts |
| dedup_seconds | 600 | Same scope/task/evidence/provider/question-set fingerprint suppression |
| max_request_bytes | 16384 | Serialized request-body size cap before credentials/network |

CLI flags mirror those names with hyphens. Failed and interrupted attempts are not refunded automatically. Reservations are journaled before dispatch, so parallel processes cannot all bypass the limit; no network work runs under the lock. These are local dispatch/size caps, **not a dollar billing guarantee**. Manual `decision_shadow` remains a separately authorized diagnostic path and is not governed by this automatic-plan budget.

Automatic provider dispatch uses one bounded **local OS subprocess**, not a Codex SubAgent. Native credential faults cannot crash the planner; a whole-process deadline of configured transport timeout plus one second stops a stuck prompt or transport and returns the original plan. There is no retry. Credential bytes are resolved inside that child, never sent in argv or JSON; core dumps are disabled where supported. API usage after a killed in-flight request remains unknown, not zero.

## Evidence and trigger contract

The original plan request remains valid. To qualify for a checkpoint, provide optional `decision_context` selecting one active task plus an existing bounded decision state. Task family and scope must match the selected task; actual facts or verification evidence are required. A deep classification alone is not enough.

Missing evidence, micro/completed tasks, no checkpoint, disabled auto calls, duplicate context, cooldown, exhausted budget, invalid config or failed telemetry all leave the original deterministic plan usable. No code reads transcripts or project files to fabricate a provider dossier. See the shipped `examples/work-plan-shadow.json` for a **synthetic shape example**, not a production fact source.

## Observability

- `decision-events.jsonl`: considered, skipped, attempted and terminal events with bounded reasons and exact plan/checkpoint identities.
- `decisions.jsonl`: actual provider result metadata, separate API usage, baseline-axis comparison fields, no source/prompt/state text.
- `router report --all-scopes`: origins, attempts, skips by reason, attempts without terminal evidence, plan-linked results, known/unknown API usage and axis disagreements.

Missing files and skipped tasks are not counted as failed API calls. An attempted event without terminal evidence may be in flight or interrupted; it is not reported as success. Events above the 16MiB read cap or malformed history stop further automatic calls conservatively rather than treating the history as empty.

Coverage is limited to observed planner invocations. Planner linkage does not prove a natural Desktop session created the invocation, and disagreement with the Lead's axes is **not** a correctness measurement. Upgrade and reload the current Skill before judging natural-task coverage. This release does not claim savings or decision accuracy improvements.

## Acceptance requirements

- Unchanged deterministic plans when provider succeeds, fails, is disabled or budget-limited.
- Explicit opt-in, preserved credential references/timeout, no surprise legacy network calls.
- Missing-context/facts skip; no guessed facts sent to API.
- Atomic dedup and global attempt accounting; multi-process CLI integration reaches a loopback test provider once for identical work.
- Correlated plan/result/events, privacy checks, old-ledger compatibility, reporting, package/install/upgrade and four-platform CI.
- No production installation/config/Keychain/ledger changes and no paid OpenAI calls as part of development.

Real Desktop checkpoint invocation remains a post-upgrade, explicitly opted-in field check. Do not substitute offline test success for that evidence.

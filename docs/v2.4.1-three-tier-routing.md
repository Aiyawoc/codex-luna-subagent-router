# v2.4.1 三层能力路由优化

## 背景

基于近期真实使用与成本 × IQ 对比，`adaptive` 的四层 `Luna → Terra → Sol → Astra` 存在两个问题：

1. Terra 在当前参考曲线中缺少稳定的成本/能力优势，且 Luna 高 reasoning 已覆盖其相当一部分能力区间；
2. 四层模型会增加路由判定、profile、测试与升级链的复杂度，而收益不明确。

v2.4.1 将新生成的 Adaptive 自动路由收敛为三层：

```text
Luna  →  Sol  →  Astra
经济     中等     专家
```

## 目标

- Luna：默认经济层，优先承担清晰、局部、低到中等难度任务；
- Sol：中间能力层，处理 Luna 明显存在 capability gap 的困难多步任务；
- Astra：专家层，仅处理高歧义、高失败代价、架构级或独立反证任务；
- Terra 不再进入 v2.4.1 新生成的 Adaptive 自动候选；
- 保留旧 RoutePlan 2.0/2.1 的解析兼容，不把历史含 Terra 的计划直接判坏；
- 升级安装时移除本 Skill 旧版托管的 Terra profiles，避免新任务继续误选。

## 三层 Capability Gap

新计划的能力层级：

```text
luna < sol < astra
```

典型最低能力：

- Luna：机械修改、窄范围实现、普通扫描、常规验证；
- Sol：高歧义多步 debug、跨模块因果、race / concurrency / lifecycle / ordering、复杂 invariant、多个竞争根因；
- Astra：架构级高歧义、高失败代价独立审查、深度 adversarial review。

大量 read-heavy 扫描不再自动使用 Terra。优先由 Luna 在合适 reasoning 下执行；若任务同时存在明显非局部推理或高失败代价，再升级到 Sol。

## 跨层 reasoning 下限

模型 capability 与 reasoning effort 分开判断。

当 Lead 已经使用当前层的 `max`，但仍因 capability gap 向上一层路由时：

```text
next_model_effort >= medium
```

不得出现：

```text
Luna max → Sol low
Sol max  → Astra low
```

当前 bundled Sol/Astra 精确 profiles 本身从 `high` 起，因此 installed-profile 路径天然满足该下限；validator 仍显式检查这条规则，防止未来新增 low profile 或 live spawn 时回归。

## 兼容策略

- 新 RoutePlan 使用 schema `2.2`；
- schema `2.2` 的 Adaptive 自动 Worker 只允许 Luna / Sol / Astra；
- validator 继续读取旧 `2.0` / `2.1`，其中 Terra 仅视为 legacy route；
- 新文档、示例、eval、installer 不再推荐或安装 Terra；
- 用户本轮显式模型 override 仍可按 Surface capability verification 处理。

## 验收标准

1. 新 Adaptive RoutePlan 不包含 `gpt-5.6-terra`。
2. Luna Lead 的普通 read-heavy 任务优先 Luna，而不是为扫描自动升 Terra。
3. Luna Max + 高歧义跨模块竞态 → Sol high/xhigh。
4. Sol Max + 专家级高失败代价审查 → Astra high/xhigh/max。
5. `lead_effort=max` 的 upward route 若 Worker effort < medium，validator 拒绝。
6. 旧 schema 2.0/2.1 含 Terra 的计划仍可解析验证。
7. 新安装/升级后不再保留本 Skill 托管的 `terra-medium.toml` / `terra-high.toml`。
8. 原有 Sol 显式 runtime ID、P0 通信协议、并发与 instruction-budget 测试不回退。

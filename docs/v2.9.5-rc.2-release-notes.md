# Agent Router v2.9.5-rc.2 · GPT-6.2与Terra max经济备选

日期：2026-11-18（Asia/Shanghai）。基线：`v2.9.5-rc.1`（`56a409a`）。本版为 Release Candidate，继续使用独立版本与发布产物。

本版将新自动 Worker 的 Sol/Astra 更新为 **GPT-6.2 Sol / GPT-6.2 Astra**，并增加 **GPT-6.1 Terra max** 作为受限经济备选。RC.1 的 `adaptive` / `adaptive_aggressive` 所有权策略、Luna-only、并发、任务隔离、身份验证和 Decision Shadow 边界继续保留。约30%/50%仍是自然任务观察目标，不是用量配额或已实现的收益。

## 1. 当前支持集合与自动范围

| 模型 | Router支持档位 | 自动选择边界 |
| --- | --- | --- |
| `gpt-6-luna` | low / medium / high / xhigh / max | 保留原低成本基准；`luna_only`仅使用这一模型。 |
| `gpt-6.1-terra` | max | 新增受限经济备选，静态默认不变；conservative下有本地失败证据的有界升级可选，雷达择优另须满足Host证据与已授权上限。 |
| `gpt-6.2-sol` | medium / high / xhigh / max | 保留原high/xhigh基准；medium仍需精确Host档位证据和限定任务，max仍只接受用户明确指定。 |
| `gpt-6.2-astra` | high / xhigh / max | 保留原高风险、深度反证与最低能力规则。 |

这是 **Router的支持策略**，不是官方API所有可用档位的完整清单。本版不新增 Sol/Astra low 或 ultra，也不改变用户当前 Lead 的模型和effort。

静态基准仍为 `Luna → Sol → Astra`。候选能力层级增加Terra后为 `Luna < Terra < Sol < Astra`，但不会因为表中出现Terra或网页评分更高就自动走一遍模型阶梯。

### Terra max的具体资格

同时满足以下条件才进入受限经济候选：

- 非micro任务，`task_scope=bounded`；
- `verifiability=yes`，`failure_cost=low/medium`；
- `reasoning_depth=shallow/medium`；
- `task_kind`为scan、research、review、verification或other；
- 原最低能力允许使用Terra，当前Host能验证精确模型和max档位，并满足用户配置的tier、effort和成本上限。

实施、深度debug、race、lifecycle和architecture不因“经济备选”降低最低能力；原来需要Sol/Astra的任务不能降到Terra。其它Terra档位和旧GPT-5.6 Terra不恢复自动候选。

Terra资格校验要求`axes.task_kind`、`axes.failure_cost`与Worker顶层对应字段一致；最低能力为Sol/Astra的Worker不能由Terra覆盖，不能用不一致的轴值放宽边界。

conservative校准中，匹配的本地已验证失败可触发有界升级，Terra max可成为符合资格的下一候选；失败组合否决、最低能力和最多2次attempt继续有效。无需雷达也能使用这一既有证据驱动路径，但不会仅为尝试Terra而制造失败或扩大重试次数。

默认雷达上限仍为`tier_ceiling=baseline`和`effort_ceiling=baseline`。若用户要让Luna基准的合格任务比较Terra max，需要明确授权相应上限，例如`tier_ceiling=terra`、`effort_ceiling=max`；这仅允许比较，仍受原评分、成本和任务资格门约束，不强制采用Terra。完整配置见[雷达说明](../skills/codex-luna-subagent-router/references/radar-selection.md)。

## 2. 旧模型退役与配置迁移

| 原模型绑定 | 新托管Worker绑定 |
| --- | --- |
| `gpt-6.1-sol`及既有旧Sol系列 | `gpt-6.2-sol` |
| `gpt-6-astra`及既有旧Astra系列 | `gpt-6.2-astra` |
| `gpt-6-luna` | 保持不变 |
| 历史GPT-5.6 Terra | 保持历史兼容；不映射成新的6.1 Terra记录 |

现有 `sol_medium/high/xhigh/max`、`astra_high/xhigh/max` profile名称保持不变，完整升级更新其托管模型绑定；Terra max为新增profile。因此，原`routing.json`无需为了本次模型更新而改写，已有模式、并发、校准、Token统计、Decision和Radar启用状态均保留。

“退役”指退出Router的新自动候选，不表示OpenAI已宣布关闭这些服务。旧outcome、usage、请求/观察身份及对应价格保持原值；不把旧账本批量重标为6.2，也不把旧成功样本当作新模型的同模型能力证明。旧Lead继续识别，用户明确的本轮override仍按原规则验证，不能越过Host能力或权限边界。

RoutePlan schema 2.0的格式兼容继续保留，但旧格式中的退役型号自动Worker不再豁免当前模型校验；执行前必须重新生成使用当前型号的计划。历史receipt仍按原identity读取和结案，不因重新规划而改写旧请求或观察身份。

升级中的同名profile不是“当前Host已接受6.2”的证据。旧型号的capability snapshot、自然语言自报或profile昵称不能替代新型号的精确绑定；无法证明时保留原保守处理。

## 3. 网页相对评分：已接入，默认关闭

本项目已有网页评分获取和择优流程，RC.2沿用并更新候选模型：

1. `route_advisor plan`先完成委派收益、能力、依赖、所有权、运行健康和容量检查。
2. 仅在存在`ready_worker_ids`时，对整波获取或复用一个CodexRadar总分批次。
3. `observe`记录建议；`select`才允许在已有边界内更改ready Worker的模型、effort和profile。
4. 网页不可用、批次过期、缺少当前模型行、身份/价格等证据不完整或无足够改进时保留静态基准。

固定来源为：

`https://codexradar.com/data/codex-four-task-summary.json`

它不是全网爬虫，也不是实时智商测量。评分来自有测量窗口的固定测试批次；成本为基准中的估计值，不是用户订阅账单。普通机械查询、无ready Worker、已运行或阻塞的任务不会触发抓取；单独`recommend`不联网。

当前流程默认关闭，保留已有数据使用许可与显式配置条件；实际启用状态须以用户当前生效配置为准。网页只读获取不需要OpenAI API Key，也不发送任务正文、源码或账本。

## 4. GPT-6.2前缀与重试

官方迁移指南说明，GPT-6.2检测到对话前缀修改、模型降级、终端用户或组织变化时可能失去既有推理项。Router继续采用已有生命周期规则：

- 不为升级模型而改写历史消息、请求/观察身份或账本。
- 运行中的旧Worker不被改名冒充6.2；需要改变模型或effort的后续工作使用fresh Worker。
- retry使用新task ID和回执，仍遵守每子任务最多2次attempt。
- 通过最小Evidence Packet复用已验证事实，不承诺跨模型继承内部推理或缓存。

本版不新增Responses会话存储、历史复制或API自动重试层。当前Router职责仍是任务规划、精确派遣和证据采集。见[生命周期规则](../skills/codex-luna-subagent-router/references/lifecycle-and-context.md)。

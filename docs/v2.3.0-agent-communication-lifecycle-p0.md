# v2.3.0 Agent Communication & Lifecycle Optimization — P0

## 背景

本轮依据 OpenAI 当前 Subagents 官方文档继续优化 `$codex-luna-subagent-router`。

官方强调的关键实践：

- SubAgent 适合探索、测试、分流、总结等 read-heavy 工作；多个 Agent 会独立消耗模型与工具 token。
- 好的 SubAgent 提示应明确如何拆分、是否等待其他 Agent，以及需要返回什么摘要。
- Codex 负责启动、steering、等待结果、停止 Agent 与关闭 Agent thread；多个请求的 Agent 同时运行时，会等待所需结果再汇总。
- App 会让用户直接看到 SubAgent thread 与返回主线程的摘要，因此 Agent 间消息应同时面向模型与人类审阅。
- 子 Agent 的价值之一是把探索记录、命令、测试日志等中间过程留在自己的线程，只向主线程返回提炼结果。

此外，GPT-6 Astra Model Guidance 明确提醒：发给其他 Agent 的消息以及最终回答可能被人阅读，因此应保持清晰可读，单词和数字之间使用正常空格，避免难以阅读的压缩文本。

官方资料：

- https://learn.chatgpt.com/zh-Hans/docs/agent-configuration/subagents?surface=app
- https://developers.openai.com/api/docs/guides/latest-model

## P0 目标

在不改变 v2.2.0 成本路由核心的前提下，降低：

1. Worker 输出 token；
2. Lead 二次整合 token；
3. 主线程上下文污染；
4. 无价值 Worker 继续运行的模型/工具成本；
5. 已完成 Worker 占用并发线程容量的时间。

## P0 范围

### P0-1 Worker → Lead：Human-readable concise result contract

所有 Luna / Terra / Sol / Astra Worker 使用同一通信原则：

- 面向人类审阅，句子清楚、使用正常空格；
- 只返回会影响 Lead 决策、集成或验收的信息；
- 不返回过程叙述、重复上下文、原始大日志或整段命令输出；
- 原始内容只有作为最小必要证据时才保留短摘录；
- 默认结果目标不超过约 200 个英文单词或等量中文；证据确有必要时可以超过，不能为了满足格式而填充内容。

默认结果协议：

```text
TASK_ACK <task_id> — <current subgoal>
STATUS: completed | blocked | failed

RESULT:
<直接结论>

EVIDENCE:
<只有必要时；文件 / symbol / 行号 / 命令结论等最小证据>

VALIDATION:
<只有实际执行且影响结论时>

RISK / BLOCKER:
<只有存在时>
```

除 `TASK_ACK`、`STATUS` 和 `RESULT` 外，其余 section 为空时直接省略。

### P0-2 Lead → Worker：Human-readable compact task packet

Task packet 继续坚持 minimal-sufficient，同时新增：

- packet 本身也是人类可读消息；
- 不 minify JSON；
- `current_user_request`、`subtask_goal`、`acceptance_criteria` 使用完整、简洁短语；
- 单词、数字、符号之间使用正常空格；
- 不用去空格、缩写堆叠、拼接词等方式节省 token。

### P0-3 Lead synthesis：去重而不是转贴

Worker reply 是证据，不是最终用户文案。Lead 集成时：

- 合并重复发现；
- 保留最强证据；
- 不逐字复制 Worker reply；
- 不倾倒 Agent 日志、命令输出、RoutePlan 或内部过程；
- 仅保留影响用户决策、任务结果、风险或验收的信息；
- 只有 attribution 对判断重要时才说明哪个 Worker 提供了哪条发现。

### P0-4 Wait policy

同一 wave 中：

- 默认等待所有“仍然必要”的 Worker 完成，再进行一次统一 synthesis；
- 不因第一个 Worker 返回就提前输出不完整结论；
- 如果后续 Worker 已不可能改变结论或验收，则进入 early-stop 规则，不再机械等待。

### P0-5 Early stop

如果 Lead 已获得决定性证据，某个运行中的 Worker 的预期信息价值已低于继续运行成本：

1. stop 该 Worker；
2. close 对应 thread；
3. 不再等待其结果。

典型场景：根因已经被直接证据确认，而其余 Worker 仅在寻找同类证据且不会承担独立验收职责。

### P0-6 Close completed Worker

Worker 结果被 Lead 接受且不再需要 steering 后，立即 close 对应 thread。

原则：

```text
result accepted -> no more steering needed -> close
```

不要让已完成 Worker 无理由继续占用 `max_concurrent_threads_per_session` 容量。

### P0-7 Retry lifecycle

对子任务重试：

1. 记录旧 attempt 结果或失败原因；
2. stop（若仍运行）并 close 旧 Worker；
3. 使用新 `task_id`；
4. fresh 新线程重试；
5. 每个子任务仍最多 2 个 attempt。

禁止在旧 Worker thread 中直接改变为新的独立目标。

### P0-8 P1 明确不在本轮实现

以下保留到 P1：

- `explore / review / implement / test / research` role 层；
- read-only / workspace-write sandbox 按 role 收敛；
- role 与 model/effort 解耦后的专用行为 contract；
- `agents.interrupt_message` 的 benchmark 与默认策略调整。

## 验收标准

P0 通过需同时满足：

1. 每个 bundled Worker profile 明确 human-readable、proper spacing、concise-only、no raw logs；
2. task packet 文档明确禁止 minified/难读消息；
3. 默认 Worker result 只强制 ACK / STATUS / RESULT，其他 section 按需省略；
4. 默认结果包含软长度预算；
5. Lead synthesis 明确去重并禁止原样转贴 Worker 输出；
6. lifecycle 明确 wait-needed-workers、early stop、accepted-result close、retry close-old-before-fresh；
7. 不改变 `luna_only` / `adaptive` 的模型选择规则；
8. 不提高默认每波 3 Worker 的成本上限；
9. RoutePlan 现有测试全部继续通过；
10. 新增 P0 contract 回归测试全部通过；
11. `MANIFEST.sha256` 与发布内容一致。

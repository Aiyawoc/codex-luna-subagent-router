# v2.5.0 — Evidence-Calibrated Routing

## 目标

在保持 v2.4.1 `Luna → Sol → Astra` 三层模型与 ExpectedCost / Capability Gap 设计不变的前提下，补上两个结构性短板：

1. 低阶 Lead 不再完全依赖自然语言解释路由规则；由本地确定性 Advisor 把任务分类映射到最低足够 model + effort。
2. Router 能从已经验证的真实 Worker 结果中保守学习，而不是每次都从静态规则重新开始。

本版继续优化：**可靠完成任务前提下的预期总模型成本**。

## P0 范围

### 1. Deterministic Advisor

新增 `scripts/route_advisor.py`。Lead 只负责给出低敏感、离散分类：

- `task_family`：非敏感 lowercase hyphen-case 标签；
- `task_kind`；
- `task_scope = micro | bounded | workflow`；
- `reasoning_depth = shallow | medium | deep`；
- `verifiability = yes | partial | no`；
- `failure_cost = low | medium | high`；
- `context_volume = low | medium | high`；
- 当前 Lead model + effort。

Advisor 本地、无网络、无模型调用，输出：

- `decision = lead_only | delegate`；
- model / effort / bundled profile；
- `minimum_capability`；
- static rule；
- route direction；
- history basis；
- selection reason。

三层模型仍只有：

```text
gpt-5.6-luna → gpt-5.6-sol → gpt-6-astra
```

Terra 不重新进入新自动路由。

### 2. Verified Outcome Registry

默认状态文件：

```text
$CODEX_HOME/state/codex-luna-subagent-router/outcomes.jsonl
```

可用 `CODEX_LUNA_ROUTER_REGISTRY` 或 Advisor `--registry` 覆盖。

项目场景传 `--project-root` 时，只保存项目路径的 SHA-256 指纹前缀，不保存真实路径；没有项目根时使用 `global` scope。

Registry 只允许受控 metadata：

- scope fingerprint；
- `task_family`；
- 六个分类轴；
- model / effort；
- `verified_pass | verified_fail | partial`；
- 单行、最多 200 字符的 verification summary；
- policy/router version；
- route binding；
- identity verified flag。

明确不存：prompt、用户正文、Worker 回复、源码、文件内容、完整日志、账号信息、密钥或真实项目路径。

## 保守历史覆盖

路由配置新增：

```json
"evidence_calibration": "off | conservative"
```

- 缺失时按 `off`，保持旧配置行为；
- 新安装/升级 Adaptive 时引导用户选择；
- 推荐 `conservative`；
- `luna_only` 不启用跨模型 evidence calibration。

`conservative` 规则：

1. 只读取同 scope、同 `task_family`、同六轴、同 policy version、90 天内的记录。
2. 只有 `identity_verified=true` 的 verified outcome 参与自动覆盖。
3. 同模型降低 effort：至少 2 次 verified pass，且没有该组合的 verified failure。
4. 跨模型降级：至少 3 次 verified pass；只允许 `verifiability=yes`、`failure_cost != high`、非 architecture 的任务。
5. 任意 verified failure 会阻止对应 cheaper combo 成为历史 override。
6. 静态首选组合已有 verified failure 时，沿 bundled route 向上找第一个没有同类 verified failure 的组合。
7. 自动 escalation 链耗尽时返回 `lead_only`，不继续猜第三种未声明路径。

因此历史可以证明“某类任务 Luna 已足够”，但不能仅凭少量成功样本把高风险、不可验证、架构类任务自动降档。

## 运行顺序

```text
用户任务
  ↓
Lead 生成匿名分类
  ↓
route_advisor.py recommend
  ↓
静态三层策略
  ↓
[可选] conservative verified history
  ↓
Lead / Luna / Sol / Astra
  ↓
现有 exact model + effort / RoutePlan / fresh packet
  ↓
Worker + targeted verification
  ↓
Lead adoption
  ↓
[calibration=conservative] record verified outcome
```

Advisor 失败、Python 不可用或 registry 不可读时，不改变任务语义：回退到现有 `routing-policy.md` 静态规则，不用更贵模型掩盖环境问题。

## 不在 v2.5.0 做

- Shadow rollout / 20–30 task comparison；
- provider `/v1/models` 自动 discovery；
- runtime catalog/config hash cache；
- requested-vs-observed thread metadata ledger；
- `UNKNOWN` spawn recovery 状态机；
- open-ended 0–5 capability vector；
- 多 provider data-policy routing；
- Terra 回归自动候选。

这些属于后续 P1，只有在 v2.5.0 的实际数据证明收益后再引入。

## 验收

1. Luna Lead + deep ambiguous debug → Advisor 推荐 Sol high。
2. Sol Lead + high-volume verifiable scan → Advisor 推荐 Luna 并向下路由。
3. 高风险不可验证 architecture → Astra。
4. micro task → `lead_only`。
5. 两次同组合 verified pass 可降低同模型 effort。
6. 三次安全、可验证的低阶 verified pass 才允许跨 tier downshift。
7. high failure cost / unverifiable / architecture 禁止历史跨 tier downshift。
8. verified failure 阻止对应 cheaper combo，并可触发 bounded escalation。
9. Registry 拒绝 raw prompt / 未验证 identity / 非 bundled route / 多行长 verification summary。
10. 项目 scope 只保存 hash fingerprint，不保存真实路径。
11. `evidence_calibration` 缺失默认 off；已知 v2 routing config 可安全迁移而不覆盖未知字段。
12. 根 `SKILL.md` 继续小于 6000 bytes；Worker profile `< 950 bytes` 不回退。
13. RoutePlan 2.1、通信 P0、Sol runtime ID、并发、安装迁移等既有测试继续通过。

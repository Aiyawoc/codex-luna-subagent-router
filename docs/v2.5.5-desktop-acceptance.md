# v2.5.5 — Codex Desktop 实机验收

本文用于收口 v2.5.4 / v2.5.5 在自动化测试之外仍需真实 Codex Desktop 验证的边界。自动化测试、PR CI 与 Manifest 已通过，但这些结果不能替代真实 Host/Core、真实 SubAgent 生命周期与真实 rollout 的实机行为。

## 验收目标

一次实机验收应同时回答以下问题：

1. **Q4 并发配置是否由当前 Codex Host/Core 正确解释**，而不是依赖 PATH 中外部 `codex` CLI 的版本。
2. **并发上限是否表示当前活跃 SubAgent 数**，而不是整个会话历史累计创建数。
3. **parent turn 与 child turn ID 不同时**，当前回合的子 Agent token 是否仍能正确归属到 parent turn。
4. **Completed Worker 条件复用**是否只统计本轮新增 token，且不误占并发槽位。
5. **最终回复前 preview 与 Stop 后快照**是否都能出现、口径一致，并且不会为了统计触发额外模型轮次。
6. `agent thread limit reached` 与 `server overloaded` 是否保持为不同错误类别。

## 前置条件

- 已升级至 v2.5.5。
- 在真实 Codex Desktop 会话中执行，不使用仅由测试脚本构造的合成 rollout 代替。
- 保留当前用户已有的 routing、outcome、usage 与 hooks 配置；不要为了验收清空历史数据。
- 若 token accounting / hooks 尚未启用或信任，先按安装引导完成对应问答和客户端信任审查。

## A. Q4 Host-first / CLI 解耦

### A1. 盘点现状

运行：

```bash
python3 skills/codex-luna-subagent-router/scripts/inspect_guided_install.py --json
```

记录 Q4 状态及检测到的 schema。

**通过标准：**

- 若当前 Host/Core 使用 canonical schema，`[agents].max_concurrent_threads_per_session = N` 被识别为 configured；
- 已存在 portable / 旧 V2 且语义明确时，被解释为同一个“最多 N 个并发 SubAgent，不含主 Agent”的用户语义；
- schema 冲突或无法可靠判定时保持 pending / 要求人工处理，而不是猜值；
- 外部 `codex` CLI 不存在、版本不同或不在 PATH 时，不应阻断 Router 的安装盘点、路由、native SubAgent、hooks 或本地统计。

### A2. 重写 Q4

按当前环境运行：

```bash
python3 skills/codex-luna-subagent-router/scripts/configure_subagent_limit.py --schema auto 3
```

随后再次运行 `inspect_guided_install.py --json`。

**通过标准：** Q4 变为 configured，且有效语义仍是最多 3 个并发 SubAgent，不含主 Agent。

## B. 活跃并发而非历史累计

在一个真实会话中：

1. 创建并完成 3 个 Worker，使它们进入 Completed；
2. 不删除这些历史 Worker；
3. 再提交一个新的、适合委派的独立任务。

**通过标准：**

- 3 个 Completed Worker 不应被 planner 当作 `open_workers=3`；
- 新 Worker 仍可在实际 Host 容量允许时创建；
- 若 Host 返回 `agent thread limit reached`，应原样分类为线程/驻留容量条件，而不是解释成“模型满载”。

## C. parent / child turn token 归属

提交一个会自然产生至少 1 个 SubAgent 的任务，并确保 parent 与 child 实际 turn/thread ID 不同。

在本轮结束前检查 preview，结束后检查 Stop/finalize 侧记录。

**通过标准：**

- parent transcript 当前 UserPromptSubmit 游标之后出现的 `Started` / `Interacted` activity 能定位真实 child thread；
- child token 被计入当前 parent turn 的子 Agent 摘要；
- 只有旧 Worker 的 completion activity 时，不把它误算进当前回合；
- 无法可靠关联时显示 partial / unavailable，而不是猜测或写成 0。

## D. Completed Worker 条件复用

选择一个刚完成、仍处于同一 workstream、模型/强度满足新任务最低能力、旧上下文仍有价值且不要求独立复核的 Worker。

向该 Worker 发出一个**新的 task_id / goal / acceptance criteria** 的 follow-up。

**通过标准：**

- 允许 follow-up 复用，而不是因为 Completed 状态强制 fresh spawn；
- 复用不改变 Worker 的 model/effort；
- 本轮 usage 只统计新的增量区间，不把 Worker 生命周期累计 token 重复计入；
- 同一任务 steering 不额外制造独立 outcome 样本； materially new 且独立验收的工作才可形成新 receipt。

以下任一条件出现时应改用 fresh Worker：无关任务、能力层级变化、模型/强度身份未知、权限变化、独立复核要求或 stale-context 风险较高。

## E. preview 与 Stop 快照

在会产生主/子 Agent token 的真实回合中：

1. 最终正文前调用/观察 `turn_usage.py preview` 对应输出；
2. 正常结束回合；
3. 检查 Stop 后的本地快照。

**通过标准：**

- preview 明确表示“截至最终回复前”的已知用量；
- Stop 快照可以比 preview 略晚、略大，因为 preview 命令结果与最终正文自身仍会消耗少量 token；
- 统计过程不为了“补齐数字”触发额外模型轮次；
- `non_usage_counter` 在其它累计连续性成立时只作为信息提示，不应单独把 terminal snapshot 降为 partial；
- 真正缺少基线、日志未刷盘、格式不支持或关联缺失时仍应保守降级。

## F. 错误类别

分别记录真实或可复现的以下错误：

- `agent thread limit reached`
- `server overloaded`

**通过标准：** 两者保持独立分类。未知错误只标记为“创建失败，原因未验证”，不要统一改写成模型过载。

## 建议记录格式

每个场景至少记录：

- Codex Desktop / Host/Core 版本（如客户端可见）；
- Router 版本；
- Q4 schema 与有效并发值；
- Lead model / reasoning；
- Worker model / reasoning；
- Worker 生命周期状态；
- parent session/turn 与 child thread 标识是否不同；
- preview 摘要；
- Stop/finalize 摘要；
- 原始错误类别（如有）；
- PASS / FAIL / BLOCKED；
- 失败时的最小复现步骤。

不要把完整 prompt、用户正文、Worker 回复、源码内容、密钥、账号信息或绝对项目路径写入公开 Issue。

## 最终通过条件

以下全部成立后，可将 v2.5.4 / v2.5.5 的 Desktop 实机边界视为收口：

- A：Q4 Host-first / schema-aware 配置通过；
- B：Completed 历史 Worker 不占当前并发槽位；
- C：parent/child 不同 ID 时本轮 token 归属正确；
- D：安全的 Completed Worker 复用只统计新增区间；
- E：preview / Stop 快照行为符合预期且无额外模型轮次；
- F：线程容量与服务过载错误分类保持独立。

任一场景失败时，不通过修改统计口径或放宽保守降级来“让数字变绿”；应保留原始证据并单独修复对应 runtime / parser / lifecycle 问题。

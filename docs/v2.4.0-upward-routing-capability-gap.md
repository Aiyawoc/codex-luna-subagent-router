# v2.4.0 Upward Routing / Capability Gap

## 背景

v2.3.1 的 `adaptive` 已允许 Luna / Terra / Sol / Astra Worker，但实际使用中低阶 Lead 很少主动创建更高阶 Worker。实机已验证 Luna Max 可以成功创建 `gpt-5.6-sol / high`，因此问题不是平台禁止向上委派，而是当前路由在进入模型选择前过早被普通 ExpectedCost gate 截断。

## 目标

在不把 Adaptive 变成“优先使用昂贵模型”的前提下，让低阶 Lead 对客观上存在能力差距的子任务稳定考虑更高阶 Worker：

- Luna → Terra：大型 read-heavy 扫描、探索和归纳；
- Luna / Terra → Sol：高歧义多步调试、跨模块因果、race / concurrency / lifecycle / ordering、多个竞争假设、困难 invariant 复核；
- Luna / Terra / Sol → Astra：架构级高歧义、高失败代价、需要独立 adversarial review 的窄范围任务；
- 高阶 Lead 仍可向 Luna / Terra 下放低能力需求任务。

## 核心原则

### 1. Capability Gap Gate 前置

Adaptive 在决定 `lead_only` 前必须先估计任务的 `minimum_capability`。如果最低能力层级高于当前 Lead，不能仅因为高级 Worker 单次调用更贵就跳过委派；必须先评估最低足够的更高阶 Worker。

Capability Gap Gate 的优先级高于普通 ExpectedCost gate，但仍受以下边界约束：

- 当前 Surface 必须能精确固定 model + effort；
- 缺少关键上下文且 Worker 无法自行恢复时，先补信息而不是盲目 spawn；
- 权限 / 环境 / packet 问题不能用更贵模型掩盖；
- 用户明确禁止或覆盖模型时服从用户。

### 2. 模型能力与 reasoning 分离

`Luna max` 仍是 Luna，不等于 `Sol high`。reasoning effort 提高的是同一模型的推理预算，不能替代模型 capability tier。

能力层级：

```text
luna < terra < sol < astra
```

### 3. 客观任务信号

默认最低能力建议：

| 客观特征 | `minimum_capability` |
| --- | --- |
| 清晰、局部、机械叶子任务 | `luna` |
| 大量文件 / 长材料的 read-heavy 扫描、探索、归纳 | `terra` |
| 高歧义多步 debugging、跨模块因果、race / concurrency / lifecycle / ordering、多假设反证 | `sol` |
| 架构级高歧义 + 高失败代价、独立 adversarial review | `astra` 候选，仍选择最低足够层级 |

不要用文件数量直接代表推理难度：200 文件扫描可能只需要 Terra；3 个文件的复杂竞态可能需要 Sol。

### 4. 禁止牺牲性低价试错

如果客观信号已经表明最低能力高于 Lead，不要为了“验证低价模型是否足够”先浪费一次低阶 attempt。第一次就选择最低足够的更高能力 Worker。

### 5. 高阶 Worker 应窄而贵

向上路由默认只把真正需要高级能力的子问题交给更高阶 Worker。根任务中的机械修改、扫描和集成仍由 Lead 或更便宜 Worker 完成。

默认一个 capability gap 先创建 1 个最低足够的高级 Worker；只有独立验证价值明显或任务相互独立时才增加高阶 Worker。

## RoutePlan 2.1

v2.4.0 新生成的 RoutePlan 使用 schema `2.1`，同时 validator 保留对旧 `2.0` 的兼容读取。

根级新增：

```json
{
  "schema_version": "2.1",
  "lead_model": "gpt-5.6-luna",
  "lead_reasoning_effort": "max"
}
```

Worker 新增：

```json
{
  "minimum_capability": "sol",
  "capability_gap_reason": "跨模块竞态包含多个时序假设，需要非局部因果推理"
}
```

规则：

- `minimum_capability`：`luna | terra | sol | astra`；
- schema 2.1 中每个 Worker 必须声明 `minimum_capability`；
- 当已知 Lead tier 且 `minimum_capability > lead tier` 时，必须提供 `capability_gap_reason`；
- 自动内置 Worker 的 model tier 不得低于 `minimum_capability`；
- `route_direction` 不落盘，由 validator / notice 根据 Lead 和 Worker model 自动计算为 `up / down / same`。

## 运行顺序

```text
Adaptive
  ↓
Identify Lead tier
  ↓
Classify minimum capability
  ├─ required > Lead → capability-gap route → lowest sufficient higher-tier Worker
  └─ required <= Lead → ordinary ExpectedCost gate → Lead / down-route / same-tier
  ↓
Exact model + effort verification
  ├─ available → spawn
  └─ unavailable → lead_only / resolve capability issue
```

## 验收矩阵

必须至少覆盖：

1. Luna Lead + 简单编辑 → `lead_only`；
2. Luna Lead + 大型 read-heavy scan → Terra；
3. Luna Max Lead + 高歧义跨模块 race → Sol high/xhigh；
4. Luna Max Lead + 架构级高失败代价独立反证 → Sol/Astra，最低足够优先；
5. Terra Lead + 困难因果 debugging → Sol；
6. Sol Lead + 简单扫描 → Luna/Terra 或 Lead；
7. Astra Lead + 机械叶子任务 → Lead 或 Luna；
8. `minimum_capability=sol` + 自动 Luna Worker → validator 拒绝；
9. capability gap 存在但无 `capability_gap_reason` → validator 拒绝；
10. `Luna max` 不得被视为等价于 Sol tier；
11. 旧 schema 2.0 RoutePlan 仍可验证，避免破坏已有工具链；
12. 自动 Sol route 继续使用显式 `gpt-5.6-sol`。

# Agent Router v2.7.0 — Execution Efficiency + Optional Grounded Decision Layer 最终计划与执行文档

> 状态：最终设计基线（第二版，按二八原则收敛）  
> 基线版本：v2.6.7  
> 目标首发：v2.7.0  
> 核心要求：**即使完全关闭 Jev/Laya/Decision Engine，v2.7.0 本身也必须在执行效率、Worker 可靠性和可验证性上产生明确收益。**  
> 核心边界：用户选择的主 Agent 不被静默替换；Decision Engine 永远是可选增强；确定性 Router、Codex runtime、测试与 Outcome 继续掌握最终事实。

---

## 1. v2.7.0 的重新定位

v2.6.7 已经解决了一个重要问题：复杂任务不能只因为 Astra/Sol Lead 自己能做，就忽略 Evidence/Scout、Parallel sibling、Independent analysis、Independent verification、Context isolation 等委派机会。

但继续优化时不能把项目变成“为了更聪明地路由而不断增加路由层复杂度”。本轮按二八原则，只吸收能够明确解决当前高频成本/可靠性问题的能力。

v2.7.0 由两条独立主线组成：

### A. Core Optimization（默认生效，与 Jev 无关）

必须交付并独立证明收益：

1. **Execution Shape Selection**  
   在“是否创建 SubAgent”之前，先决定最便宜的执行形态：
   - Lead 本地串行；
   - Lead 本地并行工具；
   - 独立 SubAgent。

2. **Worker Materialization Gate + Runtime Health Lease**  
   spawn 返回不再直接等于 Worker 已成功创建；必须确认真实实体化。当前 session 已证明 runtime 健康后，后续 wave 不重复支付健康探针成本。

3. **Router Arena + Deterministic Fuzz**  
   不再只证明“规则代码跑通”，而是用真实 fixture 对比 v2.6.7 baseline 与 v2.7 优化后的质量、Token、Worker 数和耗时。

### B. Optional Decision Enhancement（默认关闭）

Grounded Decision Layer / Jev / Laya-compatible provider：

- 2.7.0 只做 Shadow；
- 不改变生产 route；
- 不影响 Core Optimization；
- provider 不存在时 v2.7 Core 仍完整工作；
- 后续只有真实 Outcome/Token 数据证明收益后才进入 Advisory/Fast Path。

因此 v2.7.0 的产品价值不依赖 Jev。

## 2. 二八原则：本轮只吸收什么

经过对 jev-codex-router、Codex-Autorouter、codex-model-routing-team、codex-auto-model-router、oh-my-subagents、codex-subagent-guard、codex-astra-luna-orchestrator、CodexSplit 等项目的比较，本轮只吸收以下高收益部分。

| 能力 | 来源启发 | 是否进入 2.7.0 | 原因 |
|---|---|---:|---|
| Execution Shape：Local Serial / Local Parallel Tools / SubAgent | codex-auto-model-router | **是，P0** | 直接减少不必要 Worker、上下文复制和启动成本 |
| Worker Materialization Gate | codex-model-routing-team | **是，P0** | 避免 ghost Worker、错误占槽、错误统计 |
| Runtime Health Lease | codex-model-routing-team | **是，P0** | 保留首个真实 Worker 健康探针价值，又避免每轮串行探针 |
| Router Arena | Codex-Autorouter | **是，P0** | 真实证明“省 Token/时间但不降质量” |
| Deterministic fuzz / invariant tests | Codex-Autorouter | **是，P0** | Router 规则组合增长后低成本发现边界回归 |
| Shadow/Fail-open/Decision Lease | jev-codex-router | **是，可选** | 为后续 Decision Layer 建基础，但不决定 2.7 成败 |
| Stable baseline cohort | jev-codex-router | 部分吸收 | 2.7 先在 Arena 做基线，运行时 A/B 延后 |
| Canonical role layer | astra-luna-orchestrator | 延后 | 有价值，但当前不是最大瓶颈 |
| spawn_agent Guard hook | codex-subagent-guard | 延后 | Hook 竞争/桌面端兼容风险较高，收益低于前三项 |
| Durable Wave/Checkpoint Controller | oh-my-subagents | 延后 | 长期价值高，但实现范围太大，不符合本轮二八原则 |
| Model Capability Registry | CodexSplit | 延后 | 有利于未来模型扩展，但当前 Luna/Sol/Astra 体系够稳定 |
| Transport/per-call model router | jev-codex-router / codex-router | **不做** | 违反主 Agent 稳定原则，维护成本过高 |

## 3. Core Optimization 1：Execution Shape Selection

### 3.1 当前问题

v2.6.7 的重点是“找到值得独立拥有的 Worker 工作”。但“可并行”不等于“必须创建 SubAgent”。

例如：

- 同时读取 5 个互不相关文件；
- 并行做 3 个 grep/search；
- 同时读取多个 metadata；
- 两个不共享 build state 的只读测试；
- 多个机械性检查。

这些工作有时由 Lead 直接并行工具调用，比：

~~~text
spawn Luna
→ 构造 task packet
→ Worker 初始化
→ Worker 重读上下文
→ wait
→ Lead 整合
~~~

更便宜。

### 3.2 新的三态执行形态

每个非 micro 候选在 route/spawn 前增加：

~~~text
local_serial
local_parallel_tools
subagent
~~~

#### local_serial

适合：

- 强依赖前一步结果；
- critical path；
- 共享状态；
- 小任务；
- Lead 已拥有必要上下文，转交反而增加成本。

#### local_parallel_tools

适合：

- 独立 read/search/list/metadata；
- 无独立推理所有权要求；
- 无写写/读写冲突；
- 不需要独立 reviewer；
- 不值得创建新模型上下文。

#### subagent

仅在至少存在一项明确收益时：

- 独立 reasoning ownership；
- capability gap；
- context isolation；
- independent verification；
- 真正并行 sibling；
- 可明显避免昂贵 Lead exploration。

### 3.3 Execution Shape 决策优先于 model route

新的逻辑顺序：

~~~text
Candidate Work
      ↓
Execution Shape
  ├─ local_serial
  ├─ local_parallel_tools
  └─ subagent
          ↓
    route_advisor
          ↓
    Luna / Sol / Astra
~~~

不是：

~~~text
Candidate
→ 先选 Luna
→ 因为已经选了 Worker 就创建 Agent
~~~

### 3.4 目标收益

- 降低 Worker startup 次数；
- 降低 Task Packet 和上下文复制；
- 减少短小 scout Worker；
- 保留真正需要独立推理的 Worker；
- 防止 v2.6.7 “提高委派率”后走向过度委派。

### 3.5 建议实现

优先直接扩展 plan_work.py，不新增一套平行 planner。

每个 decision 增加：

~~~json
{
  "execution_shape": "local_parallel_tools",
  "execution_reason": "independent read-only evidence collection does not need a separate reasoning context"
}
~~~

当 execution_shape != subagent 时：

- 不进入 Worker groups；
- 不消耗 Worker slot；
- planned_waves 只包含真正 SubAgent；
- 输出 local_parallel_task_ids / local_serial_task_ids 给 Lead。

第一版不要求 Python 自动执行工具；Skill 按计划结果指导 Lead 使用原生并行工具能力。

## 4. Core Optimization 2：Worker Materialization Gate

### 4.1 当前问题

运行时常见状态并不是二元的“创建成功/失败”：

~~~text
spawn request
→ host 返回某种响应
→ thread/agent 可能尚未真正 materialize
→ MCP / auth / runtime 初始化可能失败
~~~

如果收到 spawn response 就立即：

- 计入 open_workers；
- 记录 Worker；
- 进入 wait；
- 创建后续 sibling；

可能产生：

- ghost Worker；
- 错误占用并发槽；
- usage/outcome 绑定错误；
- 后续 planner 误判“已有 N 个正在运行”。

### 4.2 新生命周期

v2.7 统一：

~~~text
Requested
  ↓
SpawnAcknowledged
  ↓
Materialized
  ↓
Running
  ↓
Completed / Errored / Interrupted / Shutdown
~~~

只有 Materialized 以后才：

- 计入 active/open workers；
- 绑定正式 worker_id / runtime identity；
- 开始 Outcome begin；
- 允许依赖它的后续状态进入 running；
- 将其计入 runtime health evidence。

### 4.3 Materialization 证据

按 Host 实际能力优先级：

1. spawn 返回正式 agent/thread ID；
2. list/read/status 能确认该 ID 存在；
3. 状态为 PendingInit/Running/等真实 host state；
4. 若 Host 暂无 read/list 能力，则使用现有最可靠 runtime evidence，但必须标记 materialization_source，不能伪称强验证。

### 4.4 创建失败分类

继续保留原始失败原因：

- thread/agent limit；
- server overloaded；
- permission/auth；
- MCP startup；
- model/effort unavailable；
- materialization timeout；
- runtime interrupted。

禁止统称“模型满载”。

## 5. Runtime Health Lease

### 5.1 为什么需要

codex-model-routing-team 的“第一只真实 Worker 兼作健康探针”很有价值，但如果每一轮都先串行创建 1 个 Worker，再创建其余 sibling，会降低并行收益。

因此 v2.7 只在**当前 runtime/session 尚未被证明健康**时使用健康门。

### 5.2 规则

没有有效 health lease：

~~~text
ready wave = [A, B, C]
      ↓
先创建真实任务 A
      ↓
A Materialized
      ↓
建立 runtime_health_lease
      ↓
立即并发创建 B / C
~~~

已有有效 health lease：

~~~text
ready wave = [A, B, C]
      ↓
直接并发创建 A / B / C
~~~

### 5.3 Lease 失效

命中任一：

- materialization failure；
- agent thread limit 与本地状态矛盾；
- runtime/server overloaded；
- Host/session identity 改变；
- MCP 初始化故障；
- 明确 runtime reset/restart；
- 连续 spawn 异常。

不因普通 Worker 任务失败而失效；质量失败与 runtime 健康是两件事。

### 5.4 收益

同时获得：

- 首次故障时不批量制造空壳 Worker；
- 正常 session 后续不牺牲并行性；
- 更准确的 open_workers；
- 更可靠的 usage/outcome 绑定。

## 6. Core Optimization 3：Router Arena

### 6.1 目的

v2.7 不接受“理论上更省”的结论。

需要区分：

1. route-only unit test；
2. planner/invariant test；
3. **真实 execution benchmark**。

Router Arena 专门验证第三层。

### 6.2 Baseline

每个案例至少比较：

~~~text
v2.6.7-compatible baseline
vs
v2.7 core optimization
~~~

Decision Engine 默认关闭，先证明 Core Optimization 自己有价值。

以后可增加：

~~~text
v2.7 core
vs
v2.7 core + Decision Shadow/Advisory
~~~

### 6.3 首批 fixture

至少包含：

| Case | 目的 | 预期 |
|---|---|---|
| single_known_fix | 已知根因小修改 | local_serial |
| parallel_read_scan | 多个独立只读证据 | local_parallel_tools |
| parallel_safe_checks | 无共享状态检查 | local_parallel_tools |
| deep_debug_siblings | 两条独立复杂假设 | subagent ×2 |
| context_heavy_scan | 大量上下文隔离 | Luna scout |
| implementation_plus_review | 实现+独立复核 | implementer + reviewer |
| materialization_failure | runtime 创建异常 | 不产生 ghost Worker |
| runtime_health_wave | 首次探针+后续并发 | 健康后恢复完整 wave |

### 6.4 每个案例记录

- deterministic grader；
- verified outcome；
- Lead tokens；
- Worker tokens；
- total tokens；
- cached input；
- wall time；
- Worker created/requested/materialized 数；
- retry；
- route；
- execution shape；
- failure classification。

### 6.5 发布收益门

v2.7.0 不能只做到“无回归”。

至少要求：

- parallel_read_scan / parallel_safe_checks 中，v2.7 不创建不必要 Worker，并在 total token 或 wall time 至少一项优于 baseline；
- deep_debug_siblings 仍能保持真正的 SubAgent 并行，不因 Execution Shape 优化而退回 Lead 重做；
- materialization_failure 不再把未实体化 Worker 算 active；
- consequential cases 的 verified outcome 不低于 baseline。

不预先写死百分比收益；先用真实结果决定是否有资格发布。

## 7. Deterministic Fuzz / Property Tests

随着 planner 增加 execution_shape、materialization、health lease，组合空间明显扩大。

新增 deterministic fuzz，不调用模型、不消耗 token。

建议至少覆盖 5,000 个固定 seed 组合：

- task axes；
- dependency graph；
- read/write ownership；
- completed/in_progress；
- open worker counts；
- runtime health；
- materialization success/failure；
- routing mode；
- independent_review；
- provider on/off（只验证 Shadow 不改变 route）。

必须保持的不变量：

- micro 不因新逻辑自动生成昂贵 Worker；
- local_parallel_tools 不占 Worker slot；
- conflicting writes 不进入同 wave；
- dependency 未满足不提前执行；
- materialization 失败不计 active；
- health probe 失败停止同 wave 后续 spawn；
- valid health lease 不人为串行全部 sibling；
- Decision Shadow on/off 的生产 plan 一致；
- luna_only 不被任何辅助层绕过；
- verified failure escalation 不被 Execution Shape 覆盖。

## 8. Optional Grounded Decision Layer

Decision Layer 保留，但从“2.7 主角”降为“可选实验增强”。

### 8.1 正确位置

~~~text
用户任务
→ Lead Minimum Evidence Pass
→ Core Execution Shape / Checkpoint
→ （可选）Decision Provider
→ deterministic plan_work / route_advisor
~~~

Decision Engine 只辅助：

- 六轴语义判断；
- Opportunity；
- multiple hypotheses；
- more evidence required；
- context isolation；
- independent review。

### 8.2 不改变 Core

decision_engine.enabled=false 时：

- Execution Shape 正常工作；
- Materialization Gate 正常工作；
- Runtime Health Lease 正常工作；
- Arena/Report 正常工作；
- v2.7 不退回 v2.6.7，而是保持 v2.7 Core。

### 8.3 2.7.0 只允许 Shadow

- Jev / generic HTTP / jev-codex-router /ask；
- Laya 通过 compatible HTTP；
- provider failure → unavailable；
- 不改变 model/effort/worker plan；
- 不进入 Fast Path。

## 9. Bounded Decision Dossier

仍保留代码优先构造的 bounded state：

~~~text
active_task
stage
modules
facts
uncertainties
tool_summary
error_signals
hypothesis_count
cross_module
verification_summary
~~~

预算：

- active_task <= 400 chars；
- facts <= 8；
- uncertainties <= 6；
- tool result 只保留数量、错误和最多 3 个短摘要；
- 默认 <= 8 KiB；
- hard cap 32 KiB。

不发送完整源码、完整日志、完整 tool output、完整 conversation。

## 11. 2.7 明确延后的能力

### Spawn Guard Hook

价值存在，但当前 Codex Hook 存在：

- Desktop 展示/触发回归；
- competing hook rewrite 顺序；
- V1/V2 payload 差异。

因此 2.7 不把 PreToolUse guard 作为新核心依赖。未来只能做 defense-in-depth。

### Durable Workflow Controller

OMS 风格的 Wave/Assignment/Checkpoint/Restart recovery 长期价值很高，但属于明显更大的状态机工程。

2.7 只把 Materialization 和现有 Outcome/Usage 生命周期做扎实，不扩展成完整 controller。

### Role Layer

Scout / Analyst / Implementer / Tester / Reviewer 与 model 解耦有 UX 和权限价值，但当前 routing correctness/efficiency 收益不如 Execution Shape。

### Model Capability Registry

等 OpenAI 模型集合或第三方 Worker 真正扩大后再做，当前 Luna/Sol/Astra hard-coded policy 仍可维护。

### Runtime A/B Cohort

2.7 先用 Router Arena 做受控 baseline。生产 session 稳定分流 A/B 留到有 Fast Path 后，否则数据价值有限。

## 14. 新的 2.7.0 执行里程碑

### M0 — Baseline Freeze

冻结：

- v2.6.7 baseline fixture；
- 当前 route/plan 输出；
- Outcome/Token 指标；
- Core Optimization contract。

先建立 Arena baseline，避免做完后才发现没有可比数据。

### M1 — Execution Shape

实现：

- local_serial；
- local_parallel_tools；
- subagent；
- planner 输出 reason；
- Worker wave 只包含 subagent。

验收：

- 简单只读并行不再创建 Worker；
- context isolation / independent reasoning 不被错误降成本地工具；
- existing routing tests 全绿。

### M2 — Materialization Gate + Runtime Health Lease

实现：

- Requested / SpawnAcknowledged / Materialized；
- materialization source；
- health probe；
- session/runtime health lease；
- lease invalidation。

验收：

- 未 materialize 不算 active；
- 首次 runtime 失败不会继续批量 spawn；
- 一旦健康，后续 ready wave 恢复并发。

### M3 — Router Arena + Fuzz

实现：

- 受控 fixture；
- baseline vs optimized arms；
- deterministic graders；
- token/walltime/worker metrics；
- >= 5,000 deterministic fuzz cases。

验收：

- Core Optimization 至少在目标 fixture 显示实际效率收益；
- consequential fixture 无质量回归；
- fuzz invariants 全通过。

### M4 — Optional Grounded Decision Shadow

实现：

- bounded dossier；
- provider interface；
- off/jev/http/jev_ask；
- Shadow；
- Decision Lease；
- ledger。

验收：

- provider 完全不可用不影响 Core；
- Shadow on/off 的实际 plan 完全一致；
- 不捆绑 Laya runtime。

### M5 — Report / Guided Install / Portable Runtime

report 同时展示：

- execution shape distribution；
- requested/materialized Worker；
- materialization failures；
- health lease hits；
- Lead/Worker/total tokens；
- Arena result；
- optional Decision metrics。

升级默认：

- Core Optimization on；
- Decision Engine off。

### M6 — Real-task Acceptance

至少覆盖真实 Astra 和 Sol Lead：

- 单文件已知根因；
- 多个并行只读证据；
- 多模块多假设 debug；
- context-heavy repo scan；
- implementation + independent review；
- 模拟 Worker materialization failure。

通过后才能发 v2.7.0。

## 15. 发布门

v2.7.0 必须同时满足：

### Core 行为

1. Decision Engine 完全关闭时，v2.7 Core Optimization 全部有效；
2. local_parallel_tools 不创建 Worker；
3. 真正需要独立 reasoning/context isolation 的任务仍创建 Worker；
4. 未 Materialized Worker 不计 active/open；
5. runtime health 已确认后，不再人为串行每个 wave；
6. planner 依赖/ownership/conflict 语义不回归。

### 质量与效率

7. Router Arena 的便宜并行案例在 total token 或 wall time 至少一项优于 v2.6.7 baseline；
8. consequential cases verified outcome 不低于 baseline；
9. 不增加 under-route；
10. Worker 数下降不能来自把独立 reasoning 偷回 Lead；
11. unknown usage 不写成 0。

### Decision Shadow

12. 默认关闭；
13. Shadow on/off 生产 route/plan 一致；
14. provider outage 不影响 Core；
15. 不发送完整源码/日志/prompt；
16. credential 不进入 ledger/report。

### 工程

17. >= 5,000 deterministic fuzz cases通过；
18. 全部旧测试 + 新测试通过；
19. complete manifest 通过；
20. Windows x64/ARM64、macOS x64/ARM64 portable runtime 全绿；
21. VERSION 仍是唯一产品版本源。

## 16. 2.7 的成功指标

### 不开 Jev 时

必须已经能观察到：

~~~text
不必要 Worker ↓
Worker startup/context overhead ↓
ghost Worker / 错误占槽 ↓
首次 runtime 故障扩散 ↓
只读/机械并行任务 elapsed time 或 token ↓
真正独立 SubAgent 质量保持
~~~

### 开 Shadow Decision 时

额外获得：

~~~text
confidence
disagreement
opportunity recall
decision latency
provider availability
~~~

但不改变生产行为。

### 后续 Fast Path

只有 2.7 收集的数据证明 Decision 有稳定价值时再做，不属于 2.7.0 发布条件。

## 18. 最终决策

v2.7.0 不再定义成“Jev 版本”。

它首先是一次 **Execution Efficiency + Runtime Reliability** 升级：

> **能在 Lead 内低成本完成的工作不创建 Worker；真正需要独立推理的工作继续积极委派；任何 Worker 必须真实 materialize 后才进入运行时事实；所有优化必须通过真实 Arena 和 Token/Outcome 证据证明。**

Grounded Decision Layer 保留为可选 Shadow 实验，用来为后续版本寻找进一步收益，但无论用户是否配置 Jev/Laya，v2.7.0 都应该是一版可独立成立、符合二八原则的实质优化版本。

# v2.9.4-rc.2: Verify setup, context and provider stages separately

Date: 2026-11-02. Based on released v2.9.4-rc.1. Still a candidate, not Stable; no model/permission escalation and no automatic retry.

## What the field reports actually proved

RC.1 successfully performed one controlled planner-linked API call. A later request was rejected because `decision_context.state.task_scope` was unsupported; after removing that field, another request reached a local `provider_deadline` at approximately six seconds. These observations are distinct: neither an enabled config nor an earlier standalone API test proves today's configured credential and runtime are working. No missing tokens are fabricated as zero.

RC.2 adds evidence for the missing stages. It does **not** claim that tests or a new release establish current Desktop/API availability.

## Reconfigure safely after installing the complete RC.2 package

The existing Keychain reference can be retained. Do not ask the user to paste a key into an agent tool or re-enter a key that may already be usable.

```bash
bin/router configure_decision_engine --scope user --provider openai_decisions \
  --automatic-checkpoints on --timeout-ms 30000 --total-timeout-ms 30000 \
  --credential-timeout-ms 5000 --json

# Pure configuration/context inspection: no secret or API access, no journal writes.
bin/router decision_check /path/to/request.json --global-scope

# Separate opt-in credential check. Reads the referenced credential in a bounded
# noninteractive process; never calls the API, prints or exports the credential.
bin/router decision_check --global-scope --check-credential
```

`configuration_status=valid` means the inspected values satisfy the schema and opt-in contract, not that the model is reachable. `credential_status=readable` only proves this process could read the referenced credential. `api_status=not_tested` remains until a newly authorized normal planning request receives and validates a real response. `automatic_checkpoints` is reported separately; an explicit off is not implicitly changed by inspection. Dynamic budget/cooldown/dedup admission remains a planner-time check, not a claim from this preflight.

The original state whitelist is unchanged. A scope goes in `tasks[*].axes.task_scope`, optionally also in `decision_context.checkpoint`; **never in `decision_context.state`**. Error JSON uses safe code/path/hint values and does not reflect unknown field names or submitted facts. A no-API plan remains a useful deterministic baseline, but is not a substitute for the pure `decision_check` context check.

## Visible setup, not an inaccessible agent PTY

If a credential is missing or needs the user's attention:

```bash
bin/router configure_decision_engine --scope user --open-terminal --json
```

On macOS, this creates a private `.command` and sanitized status receipt, opens **Terminal.app**, and returns `user_action_required`. A launched window is not proof the user completed setup; an exit-zero configuration receipt still says `api_tested=false` and `credential_readable=not_verified`. The user can reuse the old credential, choose a provider or enter a new key with no echo. For the same provider/scope, reuse is the default. A need for OS authorization is not evidence that the stored key is absent; never overwrite or recreate it merely because access was denied.

Hidden secret prompts are rejected on macOS when the interactive-terminal/Terminal identity checks fail. Those process markers are usability guards, not proof a human sees a window; use the explicit Terminal handoff rather than spoofing them. `getpass` must not fall back to echoing input. Non-macOS users use their own real interactive terminal; the API-free env-reference mode remains available.

The helper returns file paths for its private receipt and launcher. Keep them only until the bounded setup completes, then clean up those generated files; do not delete unrelated temporary or Keychain data.

## Time budgets and diagnostic evidence

| Setting | Meaning |
| --- | --- |
| `timeout_ms` | Timeout for blocking transport operations, 50..30000ms. This alone is not a whole-request deadline. |
| `credential_timeout_ms` | Separate waiting budget for a noninteractive credential lookup, default 5000ms, no greater than total. |
| `total_timeout_ms` | Whole provider child waiting budget, up to 30000ms. A 30000ms setting is not silently expanded to 31000ms. |

Defaults preserve prior behavior: absent explicit totals use `min(timeout_ms+1000, 30000)`. Existing user settings are not silently increased by package upgrade. A total deadline includes startup, credential work, transport and parse; process scheduling and bounded cleanup can add small observation overhead. No infinite wait is introduced.

Stages are `worker_started`, `input_validated`, `credential_lookup_started`, `credential_ready`, `transport_started`, `response_headers_received`, `response_body_received`, `response_parsed`, `completed`. Only allowlisted stage names, numeric elapsed times and HTTP status codes are accepted from the child. Parent output, correlated decision ledger and reports retain this safe metadata, never raw stderr, secret headers or raw bodies. Old ledger rows have unknown phases and are not rewritten.

`transport_started` means the local transport was invoked, **not** that a remote server accepted a request. Headers/body received can still be an authentication or schema failure. Only a validated, complete result has `available=true` and actual model/usage evidence.

`credential_interaction_required` requires a visible user action; `credential_denied`/`missing_credential` are distinct. `credential_deadline` is a bounded local lookup wait, while `provider_deadline` is the parent total budget. Transport failures use `dns_error`, `tls_error`, `connection_error`, `transport_timeout`, HTTP codes, or `response_invalid`. Cancellation after transport began can leave billing unknown; do not report zero cost.

## Validation and release gates

Mock native calls and real loopback/subprocess tests cover pointers, progress loss on timeout, typed network errors, invisible-input rejection, same-provider reuse, pure field validation and deterministic-plan isolation. They never use a live Keychain key or OpenAI account. Full source tests, exact manifests, four-platform complete packages and plugin migration/rollback must pass before publishing this immutable RC.

The remaining live gate is a controlled upgrade/configuration inspection, explicit credential check, and **at most one separately authorized API attempt** through the normal planner. Do not resend previous timed-out calls automatically. Keep `main`, Stable, historical ledgers and unrelated configuration unchanged during RC evaluation.

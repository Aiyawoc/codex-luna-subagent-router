# Agent Router v2.9 Roadmap

Baseline: v2.8.3 Stable, commit `5c3a0ef797257657cb799ed4802a47e4f3ca8ed6`.

v2.9 keeps Router as a policy/evidence layer on top of Host execution. It does
not replace Codex lifecycle, silently change the user's Lead model, or promote
experimental Native evidence merely because a new adapter exists.

## P0 — Reliability and evidence correctness

Implementation started on `feat/v2.9-reliability`.

1. **Pricing granularity**
   - A request may use the published short/long context threshold directly.
   - A receipt interval is cumulative. If cumulative input is at or below the
     threshold, every request in the interval is necessarily short.
   - If cumulative input is above the threshold and request boundaries are
     unavailable, the price stays unknown rather than assuming one long request.
   - Cost Review excludes those incomplete pricing intervals.

2. **Native Shadow same-execution identity**
   - Usage comparison requires an explicit Agents API execution identity:
     backend + session + turn + subagent.
   - Missing or mismatched identity is `inconclusive`, even if Token counters
     happen to be identical.
   - Shadow stays non-authoritative and cannot auto-promote itself.

3. **Concurrent usage collection**
   - Transcript parsing and disposable read-cache work happen outside the short
     usage-ledger write lock.
   - The final critical section reloads the latest ledger row, merges the parsed
     snapshot, then appends at most one new lifetime state.
   - Do not fix contention by blindly extending lock timeouts.

4. **Unified diagnostics**
   - `router diagnostics` is read-only by default.
   - It summarizes runtime/package, routing config, hook definitions, saved
     usage/turn ledgers, plugin ownership, Native Shadow, and report-directory
     writability hints.
   - Configured hooks are not reported as trusted/executed unless the Host
     supplies evidence; otherwise those fields remain `unverified`.
   - No prompt/tool content or local absolute paths are exported.

## P1 — Minimal Host capability snapshot and native events

After P0 is committed and regression-clean:

- represent relevant Host capabilities as `supported / unsupported / unknown`;
- initially cover only model/effort availability, exact SubAgent identity,
  programmatic tool calling, structured lifecycle events, and native usage;
- bind evidence to Host/backend/version/source rather than guessing from version;
- prefer structured Host lifecycle/usage events when actually available;
- keep rollout readers as a compatibility fallback until real Host acceptance
  proves replacement is safe.

Initial capability snapshot implementation is observational only:

- `router host_capabilities show` reads exact backend + Host-version evidence;
- `record` requires explicit confirmation and accepts only bounded sources
  (`host_runtime`, `host_api_response`, `user_verified`);
- the first capability set is Sol medium/max, exact SubAgent identity,
  Programmatic Tool Calling, structured lifecycle events and native usage;
- different sources that disagree force the capability back to `unknown`;
- capability evidence is sanitized and contains no raw session/turn IDs;
- production routing does not consume the snapshot yet.

Structured app-server event support is likewise observation-first:

- current verified v2 notification shapes are `turn/started`,
  `turn/completed`, `thread/tokenUsage/updated`, and `model/rerouted`;
- lifecycle normalization keeps thread/turn identity, terminal status, timestamps
  and a bounded error category while dropping items and error message/details;
- token usage keeps thread-lifetime `total` separate from `last` usage update.
  The notification alone is not treated as proof of a billable request boundary;
- model reroutes expose requested/observed model drift without rewriting the
  Router's historical requested route;
- explicitly confirmed normalized lifecycle/usage events may record
  version-bound capability evidence, but never production accounting authority.

## P2 — Native execution efficiency

- evaluate Programmatic Tool Calling for bounded read/filter/aggregate phases;
- keep semantic review, approvals, independent verification and risky writes
  outside programmatic batches;
- compare Host default, Router `luna_only`, and Router `adaptive` on a fixed
  workload using success rate, total cost per accepted task, latency and wasted
  Worker/tool work.

## P3 — Optional decision experiments

- Decisions API may become another optional shadow provider after its public
  contract/access conditions are verified;
- keep Laya/JEV and external providers optional and fail-open;
- never let provider availability expand model permissions, write permissions,
  concurrency, or Native authority.

## Release rule

v2.9.0 is not ready merely because P0 code exists. Before Stable it must pass
the full source/Manifest/Arena gates, four-platform complete-package and plugin
smokes, and targeted real-Host acceptance for whichever P1/P2 capabilities are
claimed as supported. Unknown evidence remains unknown.

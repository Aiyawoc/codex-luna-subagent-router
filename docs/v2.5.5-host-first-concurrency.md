# v2.5.5 — Host-first concurrency compatibility

## Why

Q4 is a semantic choice: the maximum number of concurrently open SubAgents, excluding the primary Agent. Codex config schemas changed between builds, while Codex Desktop and an external CLI can be different versions. A Skill running inside Desktop must not treat `codex --version` as the sole authority for the active Host/Core.

## Supported representations

| Representation | Stored value for 3 SubAgents | Semantics |
|---|---|---|
| Canonical | `[agents] max_concurrent_threads_per_session = 3` | Public/new schema; primary excluded. Verified in Codex 0.154.0. |
| Legacy V1 / alias | `[agents] max_threads = 3` | V1 cap; accepted as alias by newer schema. |
| Legacy V2 internal | `[features.multi_agent_v2] max_concurrent_threads_per_session = 4` | Includes the primary, so effective SubAgents = stored value - 1. |
| Portable | legacy V1/alias = 3 **and** legacy V2 internal = 4 | Same effective cap across known 0.142.1 and 0.154.0 V1/V2 paths. |

## Configuration policy

`configure_subagent_limit.py --schema auto` is the default. It preserves an existing canonical setting. If no canonical setting exists and the active Host schema is not otherwise proven, it writes the portable form instead of requiring an external CLI. `--schema canonical` is available when the **active Host/Core itself** is known to accept the canonical key.

The helper never shells out to `codex`. It parses the resulting TOML and verifies that all stored concurrency values resolve to the requested effective SubAgent limit. Conflicting representations fail closed.

## Inventory and planner

`inspect_guided_install.py` reports Q4 as configured only when the stored representation has reliable semantics for the known backend or is portable/canonical. A lone legacy V1/alias setting remains pending when the backend is unknown; a lone legacy V2 setting is accepted when V2 is explicitly enabled.

`plan_work.py` uses the same effective-cap interpretation, so the planner does not accidentally treat old V2's value (which includes the primary) as the number of SubAgent slots.

## Runtime dependency boundary

The Router depends on capabilities exposed by the active Codex Host/Core: native SubAgent tools, hooks, rollout/transcript data, config loading, and the current model surface. Local Python helpers implement deterministic routing/accounting/config manipulation. An external `codex` CLI is optional diagnostics and may be absent or a different build from Codex Desktop.

## Acceptance

- canonical 0.154-style `N=3` inventories as effective 3;
- portable `3 + 4` inventories as effective 3 without CLI;
- explicit legacy V2 `4` with V2 enabled inventories as effective 3;
- ambiguous legacy V1-only config remains Q4 pending;
- conflicting dual-schema values are rejected;
- planner honors the same effective limit;
- full existing routing/token/outcome regression remains green on Linux, macOS and Windows.

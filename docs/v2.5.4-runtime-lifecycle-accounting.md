# v2.5.4 — Runtime Lifecycle & Turn Accounting

v2.5.4 closes two real-use gaps found after v2.5.3: child usage could be omitted from the parent-turn summary because child and parent turn IDs are different, and a concurrency cap of 3 could be misread as a historical total rather than a live-capacity limit.

## Token accounting

- Parent/child association no longer assumes equal turn IDs.
- The parent rollout is read only after the UserPromptSubmit cursor; structured SubAgent activity with `Started` or `Interacted` supplies the actual child thread ID.
- Completion-only activity from an older Worker is not attributed to the current user turn.
- Existing/reused children use a per-turn cursor; only new token deltas are counted.
- `non_usage_counter` remains visible but, when continuity is otherwise valid, is informational rather than enough by itself to downgrade a terminal snapshot.
- `turn_usage.py preview` provides a pre-final body summary. It is explicitly labeled pre-final because the preview command result and final answer still consume a small number of tokens.
- Stop keeps the later hook snapshot and never triggers another model turn solely for accounting.

## Concurrency and lifecycle

`agents.max_concurrent_threads_per_session = 3` is a live concurrent spawned-agent limit, not a three-agents-per-conversation lifetime cap.

The routing workflow should read runtime status where available. PendingInit and Running consume the planner's `open_workers`; historical Completed/Errored/Interrupted/Shutdown entries do not reduce the planner's nominal free slots. Codex may still have residency-specific constraints, so a runtime `agent thread limit reached` error is handled as a runtime capacity condition rather than relabeled as model overload.

`server overloaded` is a separate service/model capacity error and follows bounded retry/wait policy.

## Conditional Worker reuse

A Completed Worker can be reused when it remains in the same parent tree/workstream, its observed model/effort is known to meet the new minimum capability, no independent review is required, and old context remains a net benefit. Reuse uses a new task ID and acceptance criteria and does not switch the Worker model/effort.

Unrelated tasks, different required model tiers, unknown runtime identity, permission changes, independent review, or high stale-context risk still use a fresh Worker.

A same-task steering follow-up does not create an additional independent outcome sample. Materially new work may create a new receipt only when separately accepted.

## Error reporting

The Lead must preserve the actual failure class:

- `agent thread limit reached` — thread/residency capacity;
- `server overloaded` — service/model overload;
- unknown/unavailable original error — creation failed, reason unverified.

The generic phrase “model full” is not used for all spawn failures.

# Agent Router v2.9.5-rc.3 · Lean Accounting + Delegation First

**状态：候选开发版；本文件不代表发布或真实Host验收通过。**

## 目标

以v2.9.5-rc.2为基线，把研发重心从自建Token计数转向更早发现适合交接的任务、更完整的Worker职责和更可信的分派落地。继续维护Model Routing、Outcome Calibration、Decision Shadow与可选Radar原有安全约束。

## 范围

1. **默认精简统计**：全新路由配置显式`token_accounting=off`；保留原始用量账本、配置与所有已有Hook授权，升级不静默改变现有已启用的统计。旧报告仍可手工调用；无需后台清理或迁移数据库。
2. **提早交接**：先获取最小真实证据，再交给Worker一份可独立验收的完整包。已有`adaptive`增加明确有界、低风险、可验证implement/test/repair交付的浅层所有权晋升；`adaptive_aggressive`继续积极交接，不放宽微任务、机械工具、失败、并发、权限和Host身份门槛。
3. **不依赖Token的反馈**：规划记录匿名worker键、候选任务数、实际计划派遣数、ready状态。materialization后的`begin`可选携带plan_id+worker_id并校验精确模型；finalize关联已有Outcome。`delegation_stats`不读取Token/转录。
4. **完整兼容**：旧历史继续保留，并保持legacy读取。未标注关联的记录一律标注无法测量，不能伪造分派比例。新指标基于**计划尝试**，不能直接与旧版30/50%的Token用量目标比较。

## 必须通过的验收

- 新安装默认Token关闭、升级旧on仍维持on；不修改用户现有Hooks/Keychain/Decision/Radar授权。
- 完整交接任务在adaptive中可有界委派；普通浅层、micro、机械查询、明确Lead保留、未验证Host及高风险边界仍受限制。
- 计划只生成ready时`linked_materialized_worker_attempts=0`，不能冒充真实派遣。只有精确scope、plan_id、worker_id、模型/档位匹配且Host已Materialized后begin，才可以登记关联回执。
- 错误plan、worker、effort或非ready必须被拒绝；验证通过、partial和pending计算正确；重复begin幂等、不重复扩大成功率。
- `delegation_stats`无网络、无Token账本读、无凭据访问；即使`usage.jsonl`不可访问仍能显示轻量统计。
- 历史outcome/planning/receipt可读，未核实实际model/effort的Worker不得被自动标为verified_pass。
- 四平台自动测试、完整/插件安装、升级与回滚均通过，真实Desktop有最小Host派遣验收后再宣布正式Stable。

## 不在本版范围

- 不提高最大单波并发3，不自动把当前用户的`adaptive`改为aggressive，不按目标强制spawn。
- 不通过第三方Benchmark扩大能力或预算上限，不自动开启Radar的网络访问和select。
- 不自行采集/导出Codex Desktop内部日志或推测其独立身份；未得到Host权威resolved model+effort时维持unverified。
- 不引入跨会话常驻监控、数据库、自动清空旧Token账本和额外模型API调用。

## 实地测试建议

先在一个普通项目scope进行15～30个可验收的中大型任务，区分adaptive与adaptive_aggressive。记录是否发现有效handoff候选、是否真正Materialized、是否独立验收、Lead有无实质返工、是否因健康/权限被阻塞。与rc.2比对时只比较定义相同的指标，不把旧规划ready和新关联begin混同。

# 当前任务包协议

每个 Worker 的初始提示词必须独立可执行。即使平台允许继承父对话，也不得把隐式历史当作任务合同。

## 强制模板

```markdown
# CURRENT TASK — <task_id>

这是一个新的当前任务。下面的任务包是本次调用的唯一有效任务合同。
不要继续任何先前 Worker、线程、项目或用户请求中的目标。
历史内容只有在本任务包明确列入“必要上下文”时才可使用。
禁止创建任何 SubAgent、后台任务或新线程。

## 身份
- root_request_id：<本轮主请求 ID>
- task_id：<本次 attempt 唯一 ID>
- attempt：<1 或 2>
- role：<inspect | mutate | verify>
- model：gpt-5.6-luna
- reasoning_effort：<medium | high | xhigh | max>

## 当前用户请求
<用户最新消息的准确原文，或在内容过长时保留关键原文并给出无损摘要>

## 本轮用户澄清
- <没有则明确写“无”；有则逐项写入问题与用户答案>

## 总体目标
<主任务最终应实现什么>

## 你的唯一子目标
<这个 Worker 本次只负责什么>

## 在整体方案中的位置
<上游输入、下游使用者、依赖关系和集成方式>

## 范围
### 必须做
- ...

### 不要做
- ...

## 必要上下文
- 只列入与本任务直接相关、仍然有效的事实和决策
- 不要倾倒完整历史聊天

## 资源与位置
- 工作区根目录：
- 当前分支/基线：
- 可读取文件：
- 可写入路径：
- 禁止触碰：
- 日志、文档或工具：

## 约束
- 用户约束：
- 技术约束：
- 权限与安全边界：
- 与其他 Worker 的接口：

## 验收标准
- ...

## 必须运行的验证
- ...

## 输出契约
最终回复必须依次包含：
1. `TASK_ACK <task_id> — <用一句话复述当前子目标>`
2. `STATUS: completed | blocked | failed`
3. 结论或完成结果
4. 证据、修改和文件引用
5. 验证及结果
6. 风险、缺口和需要主 Agent 判断的问题

如果 task_id、当前用户请求、子目标或验收标准缺失，请返回：
`PACKET_INVALID <task_id-or-unknown>`，列出缺失字段，不要猜测或继续旧任务。
```

## 构造规则

1. `task_id` 每个 attempt 唯一，推荐格式：`<root_request_id>-w<序号>-a<尝试号>`。
2. “当前用户请求”必须来自本轮最新消息，不得从旧 Worker 线程复制。
3. 若本轮调用过 `request_user_input` 或普通对话澄清，用户答案必须同时进入“本轮用户澄清”、总体目标、约束或验收标准中的适用位置；不得只保存在主 Agent 的隐式记忆中。
4. “必要上下文”只保留仍有效且与子任务直接相关的内容。
5. 所有路径、分支、错误信息和验证命令应具体到 Worker 可以立即执行。
6. 多 Worker 场景中，每个任务包都必须完整，禁止使用“同上”“继续之前”“处理这个”等隐式指代。
7. 用户看到的任务简报必须与“你的唯一子目标”语义一致。
8. follow-up 只能澄清或补完同一 `task_id` 的同一目标；目标变化时必须新建 task。

## 主 Agent 验收

采纳结果前逐项检查：

- `TASK_ACK` 中的 task_id 是否完全匹配；
- Worker 复述的目标是否是本轮子目标；
- 是否出现旧项目、旧用户请求或已失效约束；
- 本轮用户澄清是否已经反映在目标、范围、约束和验收中；
- 是否越过读写边界；
- 是否完成验收标准和必要验证；
- 是否与其他 Worker 的结果冲突。

任何身份或目标不匹配都视为 `STALE_CONTEXT`，结果不得进入最终交付。
